## 1. Contexte

[Foresight](https://github.com/vcapton-jpg/polymarket-ai) (alias polymarket-ai)
est une plateforme d'intelligence temps réel sur Polymarket : elle ingère des
news, les regroupe en événements, fait du hybrid search sur les marchés
correspondants, fait analyser l'impact par GPT-4o, et émet un **signal** noté
0-100 indiquant à un trader s'il faut acheter YES ou NO.

Aujourd'hui, le score est calculé par une **formule heuristique** :

```
signal_strength = 0.15·freshness + 0.10·source_weight + 0.15·confirmation
                + 0.60·(0.65·impact_strength + 0.35·llm_confidence)
trade_quality   = 0.40·liquidity + 0.35·spread + 0.25·time_to_resolution
signal_score    = 0.75·signal_strength + 0.25·trade_quality
```

L'audit interne (BLUEPRINT.md, section 17.2) montre un **winrate global à T+24h
de 46-48 %** — sous le hasard. Le scoring heuristique a atteint sa limite : il
ne capture pas les non-linéarités ni les interactions entre features.

**Ce projet remplace cette formule par du machine learning supervisé.**

---

## 2. Problème ML

**Tâche :** classification binaire supervisée.

**Cible (label) :** `signal_outcomes.direction_correct` — pour chaque signal
historique, le mouvement de prix réel à T+24h confirmait-il la direction
prédite ? Boolean → 0 / 1.

**Pourquoi ce label plutôt qu'un autre :**

- Disponible **24h après l'émission** du signal → beaucoup plus de samples que
  `outcome_label` (résolution finale du marché, qui peut prendre des semaines).
- Naturellement aligné avec ce qu'on veut remplacer : "est-ce que ce signal
  aurait été gagnant ?"
- Compatible avec les 3 types de modèles (LogReg / RF / MLP).

**Volume de données attendu :** entre 200 et 2000 signaux historiques avec
`direction_correct IS NOT NULL`. Sweet spot pour comparer 3 modèles sans
sur-engineering.

## 3. Décisions prises pendant le brainstorming

Récap des 5 questions structurantes (référence : conversation 2026-05-05) :

| # | Question | Choix | Justification |
|---|---|---|---|
| 1 | Nature du projet | POC pédagogique + intention de réutiliser plus tard | Le best model pourra revenir dans Foresight pour remplacer (ou compléter) la formule actuelle |
| 2 | Cible de prédiction | `direction_correct` à T+24h | Maximum de samples disponibles, label binaire propre, narrative claire pour le jury |
| 3 | Volume de données | 200-2000 signaux | Permet train/val/test classique sans synthétique |
| 4 | Structure des repos | 3 repos séparés (ml + backend + frontend), ML-first calqué sur Basile | Respecte la consigne école "split en 3 parties" et garde le repo ML aligné sur la référence |
| 5 | 3e modèle | MLP simple (Keras) | Touche au DL sans sur-promettre, reste comparable en tâche binaire |

**Métriques retenues :** accuracy, precision, recall, F1-score, ROC-AUC,
matrice de confusion, log-loss. Critère de sélection du best model :
**ROC-AUC** sur le validation set.

**Comparaison vs baseline :** l'heuristique actuelle (formule de Foresight) est
recalculée sur le test set comme **baseline à battre**. Si le ML ne la bat pas,
on l'écrit honnêtement dans le rapport.

## 6. Données : extraction, cleaning, feature engineering

### 6.1 Tables sources dans Foresight

D'après `BLUEPRINT.md` section 5 :

| Table | Colonnes utilisées |
|---|---|
| `signals` | id, event_id, market_id, direction, market_price_at_signal, source_tier_mix (JSONB), created_at |
| `signal_outcomes` | direction_correct (**LE LABEL**), move_t24h_pct (analyse seulement) |
| `event_market_features` | freshness, source_weight, confirmation, liquidity, spread, time_to_resolution |
| `event_market_analysis` | impact_strength, confidence, ambiguity_score, specificity_score |
| `events` | bucket, articles_count, unique_sources_count |

### 6.2 Requête d'export (`scripts/export_from_foresight.py`)

```sql
SELECT
  s.id AS signal_id,
  s.created_at,
  s.direction,
  s.market_price_at_signal,
  s.source_tier_mix,
  -- 6 features heuristiques
  emf.freshness, emf.source_weight, emf.confirmation,
  emf.liquidity, emf.spread, emf.time_to_resolution,
  -- 4 features LLM
  ema.impact_strength, ema.confidence AS llm_confidence,
  ema.ambiguity_score, ema.specificity_score,
  -- contexte event
  e.bucket, e.articles_count, e.unique_sources_count,
  -- LABEL
  so.direction_correct,
  -- bonus pour analyse (PAS feature)
  so.move_t24h_pct
FROM signals s
JOIN signal_outcomes so ON so.signal_id = s.id
JOIN event_market_features emf
  ON emf.event_id = s.event_id AND emf.market_id = s.market_id
JOIN event_market_analysis ema
  ON ema.event_id = s.event_id AND ema.market_id = s.market_id
JOIN events e ON e.id = s.event_id
WHERE so.direction_correct IS NOT NULL                -- T+24h capturé
  AND s.below_threshold = FALSE                       -- vrais signaux uniquement
  AND emf.freshness IS NOT NULL
ORDER BY s.created_at;
```

Sortie : `data/raw/signals_export_2026-MM-DD.csv` (~20 colonnes, 200-2000 lignes).

**Versioning :** export 2-3 fois pendant le projet (volume qui croît). Un
sample anonymisé de 50 lignes commité en `data/raw/signals_export_sample.csv`
pour reproductibilité par un évaluateur sans accès DB.

### 6.3 Cleaning (`src/data.py::clean()`)

1. **Drop des lignes invalides** : direction_correct NULL ; toute feature
   numérique NULL
2. **Cast types** : direction_correct → int (0/1), bool → int, JSONB
   `source_tier_mix` → 3 colonnes (tier_1_count, tier_2_count, tier_3_count)
3. **Outliers** : capping à p99 sur features non-bornées (move_t24h_pct pour
   analyse, mais pas freshness ∈ [0,1] déjà)
4. **Sanity checks** :
   - Toutes les features [0,1] sauf counts
   - direction_correct ∈ {0, 1}
   - Au moins 2 classes représentées (sinon erreur explicite)
   - Log la distribution des classes

### 6.4 Feature engineering (`src/features.py::feature_engineer()`)

**Features brutes (12) — déjà dans le CSV :**

- 6 heuristiques : freshness, source_weight, confirmation, liquidity, spread, time_to_resolution
- 4 LLM : impact_strength, llm_confidence, ambiguity_score, specificity_score
- 2 contexte event : articles_count, unique_sources_count

**Features dérivées qu'on construit (5-6) :**

- `tier_1_count`, `tier_2_count`, `tier_3_count` — dérivées du JSONB
  `source_tier_mix`
- `is_buy_yes` — `direction == "BUY_YES"` (binaire). Important parce que
  l'audit Foresight montre une asymétrie forte par direction (BUY_NO winrate
  72.7 %, BUY_YES winrate 29.2 % dans le bucket 75-89)
- `hour_of_day` — extrait de `created_at`, capture les patterns horaires
  (US trading hours vs nuit)
- `market_price_centered` — `|market_price_at_signal - 0.5|`, mesure
  l'incertitude initiale du marché (50 ¢ = max d'hésitation)

**Features catégorielles (1, one-hot) :**

- `bucket` : geopolitics / politics / sports / crypto / etc. → 5-7 colonnes
  binaires (one-hot avec `drop_first=True`)

**Total final ≈ 18-22 features.**

**Scaling :** `StandardScaler` fit sur **train only** (jamais sur full data,
sinon data leak), appliqué sur train/val/test. Sauvegardé dans
`models/scaler.pkl`. Important pour LogReg et MLP, optionnel pour RandomForest
mais on l'applique quand même par cohérence.

**Train / Val / Test split :**

- 70 / 15 / 15 stratifié sur `direction_correct`
- Idéalement stratifié aussi par mois pour éviter qu'un événement majeur
  (ex : élection) ne pollue qu'un seul split
- `seed=42` pour reproductibilité

### 6.5 Garde-fous anti-leak

C'est là où la plupart des projets école se font détruire par un prof attentif.

- **Pas de feature dérivée du futur** : aucune feature ne touche à
  `move_t24h_pct`, `price_t24h`, `outcome_label`, `price_resolved`
- **Pas de feature dérivée du score actuel** : on n'utilise PAS `signal_score`,
  `signal_strength`, `trade_quality` comme feature — c'est ce qu'on **remplace**,
  donc l'inclure serait de la triche (le ML apprendrait à copier l'heuristique
  au lieu de la battre)
- **Scaler fit sur train uniquement**
- **5-fold CV sur le train set pour le tuning d'hyperparamètres, jamais sur le
  test**

## 7. Stratégie d'entraînement et d'évaluation

### 7.1 Modèle 1 — Régression Logistique (baseline supervisé)

```python
LogisticRegression(
    penalty='l2',
    C=tuned_via_cv,           # grid search sur 0.01 → 10, log scale
    class_weight='balanced',
    max_iter=1000,
    random_state=42,
    solver='lbfgs'
)
```

- **Tuning :** GridSearchCV sur `C` avec 5-fold CV
- **Attendu :** score plancher. Si l'heuristique le bat, mauvais signe.
- **Avantage pédagogique :** interprétable. Les coefficients donnent une
  narrative claire ("impact_strength a le plus gros coef positif,
  ambiguity_score le plus négatif").

### 7.2 Modèle 2 — Random Forest (non-linéaire ensemble)

```python
RandomForestClassifier(
    n_estimators=tuned,        # 100 → 500
    max_depth=tuned,           # 5 → 20 ou None
    min_samples_split=tuned,   # 2 → 20
    min_samples_leaf=tuned,    # 1 → 10
    class_weight='balanced',
    random_state=42,
    n_jobs=-1
)
```

- **Tuning :** RandomizedSearchCV avec 30-50 itérations, 5-fold CV
- **Attendu :** probable gagnant sur tabulaire avec 200-2000 samples
- **Bonus :** `plots/feature_importance_rf.png` — top 10 features

### 7.3 Modèle 3 — MLP (Keras)

```python
Sequential([
    Input(shape=(n_features,)),       # ~20
    Dense(64, activation='relu'),
    BatchNormalization(),
    Dropout(0.3),
    Dense(32, activation='relu'),
    Dropout(0.2),
    Dense(1, activation='sigmoid')
])
optimizer = Adam(learning_rate=tuned)   # 1e-4 → 1e-2
loss = 'binary_crossentropy'
metrics = ['accuracy', 'AUC']
```

- **Training :** 100 epochs max + EarlyStopping(patience=10,
  restore_best_weights=True) + ReduceLROnPlateau
- **Class imbalance :** `class_weight={0: w0, 1: w1}` calculé depuis le train
- **Tuning :** learning_rate + dropout via 3-5 essais manuels (pas d'AutoML)
- **Attendu :** compétitif avec RF mais souvent pas mieux sur 1000 samples
  tabulaires. Honnêteté académique : si MLP < RF, on l'écrit.

### 7.4 Pipeline orchestrateur (`scripts/main.py`)

```
1.  load_raw()                        → DataFrame
2.  clean()                           → DataFrame nettoyé + log de stats
3.  feature_engineer()                → X, y avec ~20 colonnes
4.  train_val_test_split(X, y)        → 70/15/15 stratifié, seed=42
5.  fit_scaler(X_train) + transform   → X_train_s, X_val_s, X_test_s
6.  save scaler.pkl
7.  for model in [logreg, rf, mlp]:
      - tune_hyperparams(X_train, y_train) avec 5-fold CV
      - train sur (X_train, y_train) avec best params
      - evaluate sur (X_val, y_val) → log
      - save models/<model>.pkl
8.  select best_model via val_roc_auc → copie en models/best_model.pkl
9.  evaluate ALL models sur test set  → results/metrics.json
10. write model_card.json
11. generate plots/ (confusion matrices, ROC curves, feature importance)
```

Logging dans `logs/training_<timestamp>.log` : seed, versions des libs, taille
des splits, distrib des classes par split, métriques de chaque modèle, durée
d'entraînement.

### 7.5 Métriques (`src/metrics.py`)

| Métrique | Pourquoi |
|---|---|
| Accuracy | Lisibilité jury, mais trompeur si déséquilibre |
| Precision | "Quand le modèle dit 1, à quelle fréquence il a raison ?" |
| Recall | "Sur tous les vrais 1, combien le modèle attrape ?" |
| F1-score | Harmonique precision/recall, robuste au déséquilibre |
| **ROC-AUC** | **Métrique de sélection du best_model** |
| Matrice de confusion | Visu jury : où le modèle se trompe |
| Log-loss | Calibration des probabilités |

**Plot punchline :** `plots/roc_curves_comparison.png` — les 3 courbes ROC + la
courbe heuristique sur le même graphe.

### 7.6 Comparaison vs heuristique (`src/compare.py`)

Sur le test set :
1. Recalculer le `signal_score` heuristique avec la formule exacte de Foresight
2. Définir le seuil de décision (signal_score > 65 → label prédit 1, sinon 0)
3. Calculer toutes les métriques sur le baseline heuristique
4. Tableau côte à côte dans `results/metrics.md`

Exemple de tableau attendu (chiffres illustratifs) :

```
                      | Accuracy | F1   | ROC-AUC | Precision | Recall
----------------------|----------|------|---------|-----------|--------
Heuristique (formule) |   0.48   | 0.44 |  0.51   |   0.50    |  0.39
LogReg                |   0.58   | 0.55 |  0.62   |   0.58    |  0.52
Random Forest         |   0.64   | 0.62 |  0.69   |   0.65    |  0.59  ★
MLP                   |   0.61   | 0.59 |  0.66   |   0.62    |  0.56
```

- Tous les artefacts tagués avec un `model_version` qui matche le tag git de

### 8.2 Logique du `model_loader.py`

1. Lit `MODEL_RELEASE_URL` et `MODEL_VERSION` depuis env

## 11. Risques identifiés et mitigations

| Risque | Probabilité | Impact | Mitigation |
|---|---|---|---|
| Dataset trop petit (<200 signaux exploitables) | Moyenne | Élevé | Élargir la query, baisser le filtre `below_threshold`, oversampling SMOTE |
| Déséquilibre des classes (>70/30) | Moyenne | Moyen | `class_weight='balanced'` partout, métriques F1 + ROC-AUC plutôt qu'accuracy |
| Le ML ne bat pas l'heuristique | Faible-moyenne | Moyen | L'écrire honnêtement dans le rapport, c'est de la science |
| Stationnarité (les patterns du passé ne tiennent plus en prod) | Élevée | Faible (POC) | Le mentionner dans la discussion, pas un blocker pour la note |
| Leak de feature (utiliser une variable du futur par mégarde) | Moyenne | Critique | Liste blanche explicite dans `src/features.py`, code review |
| Modèle trop gros pour GitHub Release (>2GB limit) | Faible | Moyen | Quantization, ou Git LFS sur fichier dédié |

## Annexe A — Glossaire des features

| Feature | Type | Domaine | Description |
|---|---|---|---|
| freshness | float | [0,1] | Fraîcheur de la news (1.0 si <1h, 0.1 si >72h) |

| ambiguity_score | float | [0,1] | Ambiguïté détectée (haut = mauvais) |
| specificity_score | float | [0,1] | Spécificité news↔market (bas = mauvais) |
